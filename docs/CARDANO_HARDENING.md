# Cardano evidence and limitations — 6 October 2026

## External threat evidence

The read-only public search found Eternl Guard's maintainer-reported Cardano threat registry: https://github.com/Tastenkunst/eternl-guard, pinned at commit `a7afe53e1583a8393de5bdae7f329d0f9d64b4ae`. Seven entries contained six distinct payment addresses; duplicates were removed. Only addresses and provenance pointers are retained, not registry artwork or descriptions. The repository has no visible licence; do not redistribute its full dataset or code without checking permission.

`npm run evaluate:threats -w @agentfund/shared` reads public mainnet histories through Koios, without wallet access, signing or production mainnet payments. The saved diagnostic in `evidence/public-threats/diagnostic.json` found **0 high warnings across 6 available histories**. This exposes a weakness in the history heuristics. It is a partial-feature, positive-only, retrospective, correlated convenience sample. It provides neither fraud accuracy nor precision/false-positive rate; these remain null. No independently labelled legitimate cohort was found. Do not describe this as full Atlas recall or tune thresholds to make these six examples pass.

The free dashboard supports an exact-address public-source lookup for mainnet payment addresses. It displays the source, pinned revision and the distinction between a reported threat association and adjudicated fraud. An unlisted address is unknown, not safe. Preprod paid reports and payment routes are unchanged. Reports now explicitly say their assessment is experimental and unvalidated, and use history-warning labels. The source lookup is a known-list match, not a predictive model.

## Registration claims

Registration establishes registry metadata and self-declared operator claims. It does not certify competence, honesty or ownership of every listed external identity. The local funded-agent link now uses the configured collection address rather than a claimed agent name; an unrelated registrant naming itself Atlas cannot acquire the funded label. Tests cover that spoofing case. No independent real-world identity credential or trust certification is demonstrated.

## Automatic Masumi repayment

The standard Masumi integration retains a key-controlled selling return wallet. The installed Masumi skill's `references/smart-contracts.md` and bundled registry/payment documentation were checked before choosing compatibility over a protocol fork. Funds cannot be forced into our splitter before the operator controls them with this integration.

`npm run loop -w @agentfund/keeper` runs sweep → chain confirmation → distribution → chain confirmation. Durable state is written before signing operations; unresolved submissions block rather than being blindly retried. Known transaction hashes are reconciled after restart. Seven regression tests cover sequencing, uncertain outcomes and restarts. The loop runs locally, checks every 30 seconds, and has an exclusive daemon lock. Do not run manual sweep/distribution concurrently with it. A blocked state or stale lock needs transaction inspection before recovery. Hosting, process supervision and external alerts remain outstanding.

Automation reduces manual work; it does **not** remove operator custody, key dependence or the ability to stop repayment. Once earnings reach the splitter, its existing immutable allocation enforces the investor share.

## Reliability evidence

The worker publishes `/reliability` with observed paid Tasks, verified collections, historical failures and ongoing work, without report inputs/results. The initial live snapshot is **4 paid Tasks observed: 1 verified collection, 3 failures, 0 ongoing**. The three historical failures were requests that did not fund escrow before the payment deadline. They are not three verified lost payments or proven service failures. This is not an SLA or statistically validated marketplace success rate. The UI exposes these counts rather than hiding historical failures.

A deterministic stress test executes **100 simulated paid Task lifecycles** across fresh worker instances using durable Task files, checking one purchase/result/completion/report per Task and independent mocked collection evidence. This validates restart/idempotency behavior, not 100 live transactions. Existing ambiguous-submission regressions remain in place. The user plans three new paid Tasks; those are pending live evidence and cannot be counted as successes until collection is independently verified. The standard escrow unlock takes about 40 minutes from the negotiated terms; report delivery is not collection.
